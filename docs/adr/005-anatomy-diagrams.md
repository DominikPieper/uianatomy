# ADR 005: Generated Anatomy Diagrams with Override Path

**Status:** Accepted
**Date:** 2026-04

## Context

Each component page needs a visual anatomy diagram showing its slots/regions. The diagram should:

- Be consistent in style across all components
- Stay in sync with the YAML data (no drift between data and diagram)
- Be cheap to produce at scale (~30 components)
- Work for both designer and developer audiences
- Be interactive (hover a region → highlight in detail tables)

## Decision

A hybrid approach:

1. **Default:** anatomy diagrams are auto-generated as SVGs from structured `layout` hints in the YAML
2. **Override:** if a component's anatomy is too complex for the generator, a hand-authored `<component-id>.anatomy.svg` file in the component's content directory is used instead

The generator is the path of least resistance for typical components (Card, Modal, Tabs, etc.). The override path catches edge cases (Combobox with a popup layer, Tree with nested expansions, etc.) without forcing the generator to handle every case.

## Rationale

### Why generated by default

Auto-generation eliminates drift. If a slot is added to the YAML, it appears in the diagram automatically. If a slot is renamed, the diagram label updates automatically. There is no separate visual asset to forget to update.

For a single author managing 30+ components over months, this drift prevention is critical. Hand-drawn diagrams across 30 components would inevitably go stale.

### Why allow overrides

Some components don't fit a simple grid layout. A Combobox has an input, a dropdown panel that overlaps adjacent content, and items inside the panel. A Tree has hierarchical nesting that's hard to express as flat rows/columns. Forcing the generator to handle these creates either:

- An overcomplicated generator with edge cases for every possible layout topology
- Diagrams that look forced and don't communicate the component's structure well

The override path lets the generator stay simple while complex components get bespoke treatment when needed.

### Why SVG (not Mermaid, not images)

- **SVG** is text-based (versionable in Git), interactive (hover/click handlers), and scales without loss
- **Mermaid** is text-based but produces flow-diagram-style output that doesn't communicate component anatomy well
- **PNG/JPG** images can't be made interactive easily and are heavier than SVG for line art
- **HTML/CSS mockups** of real components could work but couple visual style to specific implementations, which conflicts with the canonical-first approach

### Why wireframe style

A simple wireframe style (thin lines, white fill, sans-serif labels, dashed outlines for optional slots) is:

- Neutral enough to feel reference-like rather than design-mockup-like
- Cheap to generate consistently
- Acceptable to both designer and developer audiences
- Easy to extend with hover/highlight states without visual noise

A higher-fidelity style (subtle shadows, dummy content, accent colors) was considered but rejected because it starts to feel like a design mockup, which creates subtle "is this how it should *look*?" pressure on a reference that's deliberately implementation-agnostic.

## Schema additions for layout hints

```yaml
anatomy:
  - id: media
    required: false
    layout:
      row: 1
      col: 1
      span: full              # full | half | third | quarter | numeric
      aspect: '16:9'          # optional, for media-like slots
  - id: title
    required: true
    layout:
      row: 2
      col: 1
```

The generator reads these hints and produces a wireframe SVG with:

- Solid outlines for `required: true` slots
- Dashed outlines for `required: false` slots
- Slot ID as the label
- Hover state that highlights the corresponding row in the detail tables

## Override convention

If a file `content/components/<id>.anatomy.svg` exists, it is used instead of the generated diagram. The override SVG must:

- Use `<g id="slot-<id>">` or `<rect id="slot-<id>">` for each slot, matching the YAML anatomy IDs
- Use the project's wireframe style (defined in `shared/styles/wireframe.css`) for visual consistency
- Be no larger than 800px wide

The site build validates that override SVGs reference all and only the slots defined in the YAML — preventing drift between hand-drawn diagrams and data.

## Consequences

**Positive:**

- 70%+ of components get a free, drift-proof diagram from data alone
- Complex components retain authorial control via overrides
- Visual style is automatically consistent for generated diagrams; enforced via shared CSS for overrides
- Diagrams are interactive (hover-to-highlight) by default

**Negative:**

- Two render paths in the build (generator + override loading)
- Override SVGs require hand-authoring, with all the maintenance that implies — but only for components that genuinely need it
- The generator needs to be built; this is non-trivial work upfront

**Neutral:**

- A future enhancement could allow inline annotations (arrows, callouts) on diagrams; deferred until there's clear demand

## Phase 1 implementation order

1. Build the generator with simple components (Card, Modal) as test subjects
2. Validate the wireframe style with both component types
3. Use override path for the first complex component encountered (likely Combobox)
4. Refine the generator only if a pattern of overrides reveals a generalizable improvement

## Alternatives considered

**Hand-drawn for all components:** rejected. ~30 × 30 minutes = 15 hours upfront, plus ongoing drift risk.

**Generator only, no override path:** rejected. Forces complex components into simplified diagrams that don't communicate their anatomy well.

**Live-rendered HTML/CSS mockups:** rejected. Couples visual style to specific implementations and creates pressure on the canon to look "designed."

**Mermaid or D2 diagrams:** rejected. Wrong visual register for component anatomy; better suited to flow charts and architecture diagrams.
